# 删除与回收站设计

## 目标

让家人能删照片，且删错了能找回来。这是 README 里最劝退的一条限制：新用户第一次
用就会问「怎么不能删」。

两条硬要求：

1. **不能真丢**。没有个人账号，没有操作日志，删错一次就是永久损失。
2. **删了就真的不可见**。软删除不只是列表里隐藏，已打包的 ZIP、分享链接里的原图
   也必须立刻失效，否则「删掉的私密照片还能被下载」是严重问题。

## 现状

`photos.deleted_at` 和 `albums.deleted_at` **已经存在**，并且所有读路径都已过滤：
相册列表、封面回退、照片计数、拍摄时间范围、签名读取、下载任务、分享列表。

所以读取侧零改动，缺的是写侧：没有删除接口、没有回收站页面、没有清理 worker。

## 数据模型

```sql
ALTER TABLE photos ADD COLUMN deleted_by TEXT NOT NULL DEFAULT '';
ALTER TABLE photos ADD COLUMN trash_batch TEXT NOT NULL DEFAULT '';
CREATE INDEX IF NOT EXISTS photos_trash ON photos(deleted_at) WHERE deleted_at IS NOT NULL;
```

- `deleted_at` 已有，复用
- `deleted_by` 记录删除者的名字（客户端本地名字，仅用于展示，不是身份）
- `trash_batch` 让「删除整个相册」可以原子恢复：一次操作一个批次 id

**软删除会自动退出去重的唯一索引**（索引条件含 `deleted_at IS NULL`），所以删除后
可以重新上传同一张照片；恢复时如果相册里已经有同内容照片，把恢复行的 `dedup_key`
置为 NULL（等价于用户勾了「仍然添加」），不阻塞恢复。

## 权限

没有个人账号，`contributor` 是客户端传的、不可信，服务端无法验证「是不是我传的」，
所以只能按角色分：

| 操作 | 家庭成员 | 管理员 |
| --- | --- | --- |
| 移到回收站 | ✅ | ✅ |
| 从回收站恢复 | ✅ | ✅ |
| 永久删除 / 清空回收站 | ❌ | ✅ |
| 删除相册 | ❌ | ✅ |

与现有的破坏性操作（导入、关闭收集、改相册）一致，都走 `requireAdmin`。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/photos/trash` | 批量软删除，`{ids:[]}`，返回 `{trashed, batch}` |
| `POST` | `/api/v1/trash/restore` | 批量恢复，返回 `{restored, albums_restored}` |
| `GET` | `/api/v1/trash` | 回收站列表 + 总占用 + 保留期 |
| `DELETE` | `/api/v1/trash` | 清空（admin，立即永久删除） |
| `DELETE` | `/api/v1/albums/{id}` | 删除相册并级联（admin） |

`GET /trash` 响应：

```jsonc
{
  "items": [{ "id", "name", "album_id", "album_name", "thumb_url",
              "contributor", "deleted_by", "deleted_at", "size" }],
  "total_bytes": 12345678,
  "retention_days": 30,        // 0 表示永久保留
  "expires_at": "2026-12-23T…" // 最早一批的到期时间，无则空
}
```

## 三个必须处理的细节

### ① 封面悬空

被删照片如果是相册封面（`albums.cover_photo_id`），必须同时清空 `cover_key` 和
`cover_photo_id`，让相册回退到「最新一张」的默认逻辑（那条子查询已过滤
`deleted_at`，会自动跳过已删的）。否则封面变成坏图。

### ② 已打包的 ZIP 仍然含这张照片

`download_packages` 里的 ZIP 已经是 S3 上的对象，里面是删除前的字节。**软删除时
必须把这个照片从相关下载任务里剔除**，否则用户删掉的私密照片还能从旧下载链接拿到。

做法：找出 `photo_ids` 包含目标照片的下载任务，删除其 package 对象与记录，并删掉
任务行（这类行本来就只保留 24 小时）。失败时保守处理：宁可让用户重新打包。

### ③ 软删除不释放空间

S3 对象还在。界面必须写清楚「空间在 N 天后释放」，否则管理员会疑惑「删了怎么没变」。
回收站页顶部显示已占用空间。

## 清理 worker

复用现有 `RunWorker` 的单循环模式。每轮：

1. 取 `deleted_at < now - TRASH_RETENTION` 的照片
2. **先删 S3 对象**（original → preview → thumb）
3. 成功后再删数据库行

顺序不能反：反过来一旦 S3 删除失败，就留下永远找不到的孤儿对象。S3 失败则保留行，
下轮重试。

`TRASH_RETENTION=0` 表示永不自动清理（有些家庭就是不想自动删）。

## 保留策略

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `TRASH_RETENTION` | `720h` | 30 天；`0` 表示永久保留 |

## UI

| 位置 | 改动 |
| --- | --- |
| 照片网格右键菜单 | 加「移到回收站」 |
| 多选底栏 | 加垃圾桶按钮 |
| 删除后 Toast | 带「撤销」，8 秒内可撤销（复用现有 Toast，加一个 action） |
| `/trash` 页面 | 网格 + 多选 + 恢复 / 永久删除 / 清空 + 保留期横幅 |
| 侧栏 | 回收站非空时显示入口 |
| 确认 | 移入回收站**不弹**确认（可撤销）；永久删除**必须**二次确认 |

## 恢复的边界

**相册已被删，单张照片怎么恢复？**

自动把相册一起恢复，并提示「已同时恢复相册《XX》」。拒绝恢复会让长辈看到「无法恢复，
请先恢复所属相册」这种看不懂的错误。

**恢复时相册里已有同内容照片？**

把恢复行的 `dedup_key` 置 NULL，正常恢复。不报错，因为用户目的就是「把这张拿回来」。

## 测试

- 软删除后：列表 / 相册计数 / 签名读取 / 分享页都看不到
- 删封面照片后相册封面回退
- 已打包任务被清除，旧签名链接失效
- 恢复后照片回到原相册，计数正确
- 恢复被删相册里的照片会自动恢复相册
- 清理 worker：到期照片的 S3 对象与数据库行都被删除；S3 失败时行保留
- 管理员权限：家庭成员不能永久删除
