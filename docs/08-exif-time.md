# 拍摄时间（EXIF）

## 问题

页面上每个相册的照片都归在「November 23, 2026」——上传当天。原因是
`photos.taken_at` 一直写的是**上传时间**：

```go
timestamp := now()
INSERT INTO photos(..., taken_at, created_at) VALUES (..., timestamp, timestamp)
```

对一个家庭相册来说这几乎摧毁了「按时间回想」的价值：2019 年的旅行照片和今天的截图
混在同一天里。

## 为什么在浏览器解析

项目约束是**原图不经过应用服务器**，所以服务端全程看不到字节。可选做法：

| 做法 | 代价 |
| --- | --- |
| 服务端从 S3 读回原图解析 | 每个上传多读一遍完整文件，违背设计初衷 |
| 上传前把 EXIF 单独发上来 | ✅ 只需几 KB，且解析发生在客户端 |

还有一个更根本的理由：**EXIF 存的是当地挂钟时间，没有时区**。`2026:08:03 10:11:12`
究竟是北京时间还是柏林时间，只有上传者的浏览器知道。在浏览器里 `new Date(...)`
会按本机时区解释，直接得到正确的 UTC 时刻；放到服务端解释就会错几个小时。

## 实现

`web/src/lib/exif.ts`，纯函数、无依赖、不抛异常（损坏的 EXIF 不能阻断上传）：

```
findTiffStart()   在字节里定位 TIFF 头
makeReader()      按 II/MM 选择字节序
readIfd()         遍历 IFD 条目
readAscii()       读取 ASCII 值（日期就在这里）
parseExifDate()   校验并构造 Date
```

### 两种容器，一个 TIFF 头

| 容器 | Exif 位置 |
| --- | --- |
| JPEG | APP1 段（`FFE1` + 长度 + `Exif\0\0`） |
| HEIC / HEIF | ISOBMFF Exif item，同样以 `Exif\0\0` 开头 |

JPEG 走**段链遍历**而不是全文件搜索：图像数据里出现 `Exif\0\0` 字样是可能的，
按段长度跳跃才不会认错。其他格式退化为「找到标记 + 校验 TIFF 头」。

### 读取顺序

1. `DateTimeOriginal`（0x9003，Exif 子 IFD）——拍摄瞬间，最准确
2. `DateTimeDigitized`（0x9004）——次选
3. `DateTime`（0x0132，IFD0）——很多相机只写这个

### 严格的日期校验

- 拒绝 `0000:00:00 00:00:00`，不少相机用它表示「未设置」
- 拒绝 `2026:02:31`：`new Date` 会自动滚到 3 月 3 日，必须回读校验
- 拒绝 1900 年之前、以及比现在晚 24 小时以上的时间戳

最后一条很重要：手机时钟错乱时会产生未来时间，而未来时间会排在相册最前面，
比「用上传时间」更糟。

## 数据流转

```
浏览器读 EXIF → 转成 RFC3339 UTC
   ↓ POST /uploads { taken_at }
upload_sessions.taken_at        （新增列）
   ↓ 完成上传
photos.taken_at                 ← 有值就用它，否则用上传时间
```

访客链路同理：`submission_items.taken_at`，导入时一并写进 `photos.taken_at`。

服务端仍会校验一遍 `cleanTakenAt()`：只接受 RFC3339、且落在合理区间内。**不可用的值
被丢弃而不是拒绝**——文件本身没问题，只是缺时间戳，不该因此上传失败。

## 效果

用一张 EXIF 写着 `2026:08:03 10:11:12` 的照片，在 `Asia/Shanghai` 时区的浏览器上传：

```
stored taken_at:  2026-08-03T02:11:12Z
```

正是 +08:00 换算。界面上分组标题显示「August 3, 2026」，而不是上传当天。

## 边界

| 情况 | 行为 |
| --- | --- |
| 文件没有 EXIF | 回落到上传时间（旧行为） |
| EXIF 损坏 / 截断 | 同上，不报错 |
| 时间在未来（时钟错乱） | 丢弃，用上传时间 |
| 时区未知的挂钟时间 | 按上传者本机时区解释 |
| 已经上传过的旧照片 | **不变**，仍按上传时间排列 |

最后一条是已知限制：回填旧照片需要从 S3 读回原图，代价与 `DEDUP_BACKFILL` 相同。
有这个需要的部署可以参照那个开关另做一次迁移，当前没有实现。

## 测试

- `exif.test.ts` 用一张 Pillow 生成的真实 JPEG（大端 TIFF）作为 fixture，
  并构造小端、仅 `DateTime`、非法日期、截断块等合成用例
- `api_test.go` 的 `TestCleanTakenAt` 覆盖 UTC 归一化、越界与非法值
- 端到端：上传带 EXIF 的真实 JPEG，确认存储值与界面分组都按拍摄日期

## 未做

- **HEIC 的方向标签**（Orientation）：libheif 解码时已应用旋转，但写入的
  `width`/`height` 是解码后的尺寸，与显示一致，无需额外处理。
- **旧照片回填**：见上。
- **时区偏移标签**（`OffsetTimeOriginal`，0x9011）：有的话可以更精确，但绝大多数手机
  不写，且当前方案已经正确。
